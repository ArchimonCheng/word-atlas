# Word Atlas 词汇图谱

输入一个英文单词，得到一份四维结构的「词汇档案」：溯源构词、发音重音、词频语境、语法产出。档案由知乎直答按固定框架生成，并同时附上知乎站内讨论与全网权威来源。

参赛活动：知乎黑客松 2026 校园新锐季（`zhihu_hackathon_2026_p2`）

## 核心创作思路

市面上的查词工具给的是「释义 + 例句」，解决的是「这个词什么意思」。真正卡住学习者的是另外三个问题：这个词能不能拆、重音在哪、值不值得花时间背。

Word Atlas 把一套已经成型的分析方法固化成产品。它不是让 AI 自由发挥，而是给 AI 一个不能偏离的框架和一组硬约束，输出形态在每次调用之间保持一致。

最关键的设计取舍是**允许档案留空**。词源、COCA 词频、CEFR 等级恰好是最容易被语言模型编造的三类信息。产品要求模型查不到就写「待核查」，而不是猜一个看起来合理的数字填进去。一份有明确空缺的档案比一份看起来完整但局部失真的档案更有价值——后者会被当成已核实的知识记住，纠正成本更高。

## 目标用户

- 备考人群（考研、雅思托福、GRE）：需要判断生词优先级，而不是无差别地背
- 英语写作者：需要搭配和语域信息，不只是中文释义
- 词根词缀学习者：需要可靠的构词拆解，以及「这个词不能拆」的明确判断

## 用户如何完成核心体验

1. 打开首页，直接在页面中央输入英文单词，可选填中文释义（用于让检索更贴近该词本身）
2. 选模型档位：深度思考（约 60–180 秒，先展示推理过程）或快速回答（十余秒）
3. 档案以流式逐字呈现，边生成边分流到四张彩色卡片，不等全文生成完
4. 两侧同时给出知乎站内讨论与全网权威来源，可点进原文
5. 页面底部横贯的进度条展示当日 API 额度，下方按接口分列明细
6. 每次成功生成自动记入本地历史，下方给出词根与词的双向统计

不强制登录，核心功能无需授权即可完整使用。

### 界面上的几处设计

- **四维卡片**：四张卡片各有主色（紫／青／琥珀／绿），可拖动重排，也可用键盘按钮移动
- **词根着色**：从「拆解」行提取词素后，给标题词分段上色；不可拆的词（如 `brine`）不着色
- **拆解两行呈现**：第一行是彩色词素块，第二行是模型原文说明
- **语义路径流水线**：本义 → 引申义 → 当代义按箭头切成带编号的竖向步骤
- **列举分行**：同根词族、高频搭配、例句等多项内容逐项独立成行，不挤在一行里用标点分隔
- **深浅主题**：默认跟随系统，手动选择后记住偏好；浅色模式下卡片与词根配色换用加深变体
- **历史与词根统计**：左侧「词根 → 词」按出现次数排横条图，点击可筛选；右侧「词 → 词根」列出词素与 IPA，点词名可重新生成

## 技术方案

后端 Python 标准库 `http.server` + `requests`，无 Web 框架依赖；前端原生 HTML/CSS/JS，无构建步骤、无前端依赖。`python3 app.py` 即可启动。

```
app.py                    后端：直答 SSE 代理、两类搜索、额度、OAuth
static/index.html         前端：渲染、卡片、历史统计、主题
tests/test_oauth_flow.py  OAuth 全流程测试（mock 上游）
Containerfile             容器构建，平台通用
```

关键实现点：

- **框架注入位置**：实测直答会忽略 `system` 角色的指令（同一条指令放 `system` 被无视、放 `user` 轮严格执行），因此四维框架整体拼进 `user` 消息，硬约束重申在末尾利用近因效应。这是本项目最重要的一处调试结论。
- **SSE 流式转发**：上游 `text/event-stream` 未声明 charset，`requests` 会按 ISO-8859-1 解码导致中文乱码；改为按 UTF-8 增量解码，并自行缓冲跨 chunk 的不完整行，避免长 data 行被切断后静默丢弃。同时跳过 `: keep-alive` 心跳。
- **流式分卡渲染**：前端自行实现极简 Markdown 解析（先转义再解析，模型输出中的 HTML 不会执行），按 `## 一、～四、` 增量切分，哪一维出来了就先渲染哪一维。
- **两类来源分开呈现**：站内搜索给社区经验，全网搜索给词典与机构来源，分别调用、分别展示，不混成一个黑盒。全网结果剥掉 `<em>` 高亮标签，并按 `AuthorityLevel` 标注权威等级。
- **额度保护**：搜索与额度查询走 15 分钟 TTL 缓存 + 同 key 请求去重（双重检查加锁）；分析接口按 IP 限流 8 次/分钟，其余接口 20 次/分钟。两类搜索使用独立缓存键前缀，同一词不会被重复查询。
- **凭证边界**：Access Secret、App Key、OAuth Token 只存在于后端进程环境与服务端会话；`/api/health` 诊断只暴露来源、是否配置、长度与 SHA-256 短前缀。前端任何响应都不含凭证。
- **访问日志遮蔽**：默认请求行含 query，`/auth/callback?authorization_code=…` 会把授权码写进日志。日志会被打包、截图或贴进 issue，因此对 `authorization_code`、`code`、`token`、`app_key`、`state` 等键的值统一替换为 `<redacted:N>`，保留键名与长度便于排查，非敏感参数（如 `word`）原样保留。
- **会话 Cookie 的 `Secure`**：默认跟随 `ZHIHU_OAUTH_REDIRECT_URI` 的协议——回调是 `https://` 时自动开启，本地 `http` 调试保持可用（若在本地强开，浏览器会直接丢弃 cookie，登录表现为「点了没反应」）。可用 `COOKIE_SECURE=1/0` 显式覆盖；应用自身跑 http、由反向代理终止 TLS 时必须手动置 `1`。设置与清除两处共用同一构造函数，避免属性不一致导致登出时 cookie 清不掉。`/api/health` 暴露 `cookie_secure`，部署后可直接确认。
- **降级行为**：未配置 Access Secret 返回 503 并在页面显式提示；未配置 OAuth 时隐藏登录入口但保留核心功能；检索为空时提示档案仅基于模型知识；上游超时、流式中途报错、返回空内容都有对应提示，不静默失败。
- **历史存储**：纯前端 `localStorage`，上限 100 条，同词重复查询只保留最新一条；损坏数据或非数组内容返回空数组不崩。不涉及服务端存储，也不需要数据库。

### 部署约束

会话、缓存、限流状态都在进程内存里，**必须单实例**。多实例或 serverless 冷启动会导致登录态丢失，SSE 长流也可能被平台超时切断。Fly／Render／Railway 单实例或自有服务器可用；Vercel 一类多实例 serverless 不适用，除非先把会话挪到外部存储。

## 使用的知乎开放能力

| 能力 | 接口 | 用途 |
|---|---|---|
| 知乎直答 | `POST /v1/chat/completions` | 按四维框架生成档案，SSE 流式输出，两档模型可选 |
| 知乎搜索 | `GET /api/v1/content/zhihu_search` | 检索站内讨论，既喂给直答参考，也原样展示 |
| 全网搜索 | `GET /api/v1/content/global_search` | 检索词典、外刊等站外权威来源 |
| 额度查询 | `GET /api/v1/quota` | 底部进度条展示当日用量 |
| 用户数据 | `GET /api/v1/user/contents` | OAuth 授权用户的创作列表（路由保留，见下） |
| 账号 OAuth | `openapi.zhihu.com/authorize` + `/access_token` | 知乎账号登录 |

## 与社区生态的契合点

知乎上有大量高质量的词根词缀整理、外刊精读和考研词汇讲解。这些内容的问题是分散、缺乏统一结构，检索到之后仍需自己整合。

Word Atlas 把站内讨论作为档案的来源层：搜索结果既喂给直答作参考，也原样附在界面上供用户点进原文。实测分析 `conglomerate` 时，站内命中了一条正好讲 `agglomerate` 与 `conglomerate` 前缀差异的回答，直接进入了档案的同根词族部分。全网搜索则补上 Merriam-Webster、Britannica 这类词典与百科来源。

这是「结构化框架 + 社区原始内容 + 站外权威来源」三者互补，而不是用 AI 替代原文阅读。

## 对社区用户的实际价值

- 把分散的社区词汇知识收敛成稳定的档案形态，且保留原文入口
- 明确标注不确定信息，降低把编造内容当知识记住的风险
- 词频量级带给出「该不该背」的判断依据，而不只是「是什么意思」
- 词根统计让零散查询积累成个人化的构词地图：查得越多，`-ate`、`glomer-` 这类词素串起的词越多

## 本地运行

```bash
cp .env.example .env      # 填入 ZHIHU_ACCESS_SECRET
set -a; . ./.env; set +a
python3 app.py            # 默认 http://127.0.0.1:8787
```

容器方式：

```bash
podman build -t word-atlas -f Containerfile .
podman run -d -p 127.0.0.1:8787:8787 \
  -e ZHIHU_ACCESS_SECRET="$ZHIHU_ACCESS_SECRET" word-atlas
```

默认只监听回环地址。`/api/analyze` 无鉴权且会消耗开放平台额度，对外暴露前须置于反向代理或平台网关之后，再显式设置 `HOST=0.0.0.0`（Containerfile 内已设为 `0.0.0.0`，依赖平台网关做访问控制）。

运行 OAuth 流程测试：

```bash
python3 tests/test_oauth_flow.py
```
